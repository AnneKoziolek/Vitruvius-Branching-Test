# Implementation (Draft)

## Overview

We implemented the directed semantic merge as an extension to the Vitruvius framework [ref], a tool-supported approach to view-based software development that maintains consistency across multiple coupled models via change propagation rules (CPRs).
The implementation adds approximately 1,600 lines of Java to the framework's VSUM module and has been validated on two case studies with a total of 42 automated test scenarios.

The merge operates on *user transaction histories* rather than model states.
Each branch records a sequence of fine-grained EMF change events (EChanges) that represent the user's primary edits.
Derived changes—those produced by CPR execution—are intentionally excluded from the recorded history, since they can be regenerated by replaying the user changes through the CPR engine.
This separation is the key enabler for our conflict classification: because we know which changes are user-authored and which are derived, we can distinguish direct conflicts (user vs. user), indirect conflicts (derived vs. user), and benign overwrites (user vs. derived).

## Change Recording and Changelog Persistence

Each model element in the VSUM is assigned a permanent UUID that persists across branches.
We instrument the VSUM's change propagation pipeline with a `ChangeLogCapture` listener that intercepts the `finishedChangePropagation` callback.
At that point, the primary EChanges have been applied and the CPRs have executed, so we can extract the user-authored changes (those passed *into* `propagateChange`) while discarding the consequential changes produced by CPRs.

Each captured EChange is converted from the VSUM's internal UUID-based representation to a serializable DTO that records:
(i) the change type (e.g., `ReplaceSingleValuedEAttribute`),
(ii) the affected element's UUID (for cross-branch identity),
(iii) the affected feature name, and
(iv) the old and new values.
After each Git commit, the accumulated DTOs are persisted as a JSON changelog file alongside the model files, forming the transaction history $H^u$.

This design choice—recording only primary changes—means that changelog files are compact (typically 1–10 DTOs per commit) and that the merge algorithm can reason about user intent without being confounded by the potentially large number of derived changes that CPRs produce.

## Directed Merge Algorithm

Given a merge direction $A \to B$ (source into target), the algorithm proceeds as follows.

**Phase 1: State extraction.**
We use JGit's `TreeWalk` API to extract the model files and changelog files at the base, source ($A$), and target ($B$) commits into isolated temporary directories, avoiding interference with the working copy.

**Phase 2: Direct conflict detection.**
Before any replay, we compare the changelog DTOs from both branches by element UUID and feature name.
If both branches contain a `ReplaceSingleValued*` change on the same UUID and feature with different values, we report a `MODIFY_MODIFY` conflict.
Identical modifications are silently accepted.
Delete-modify conflicts are detected analogously.
This phase operates purely on the serialized DTOs without loading any model state, making it efficient even for large histories.

**Phase 3: Per-transaction replay with warning detection.**
We load the target branch's VSUM from the extracted state and replay the source branch's transactions one at a time.
For each transaction $\tau_i^u$ from $H_A^u$:

1. *User-vs-derived warning check (before replay).*
   For each change in $\tau_i^u$, we check whether the affected element exists in the target VSUM but was not explicitly changed by any user transaction in $H_B^u$.
   If so, the element's current value on $B$ was set by a CPR (derived state), and the replay will overwrite it with the user's explicit intent from $A$.
   We record a `USER_VS_DERIVED` warning but proceed with the replay.

   To perform this check efficiently, we build a map from UUID strings to live EMF objects by traversing the loaded VSUM's resource set.
   This avoids relying solely on the changelog DTOs, which by design do not contain derived changes.

2. *Replay.*
   The transaction's DTOs are deserialized into live EChange objects and applied to a `ChangeRecordingView` on the target VSUM.
   The view's `commitChanges()` call propagates the changes through the CPR engine, causing reactions to fire and derived models to update—exactly as they would during normal editing.

3. *Indirect conflict detection (after replay).*
   Before the replay, we snapshot the values of all element–feature pairs that appear in $B$'s user footprints.
   After the replay, we compare these snapshots against the current values.
   If a value changed but was not part of the source transaction's direct changes, the change must have been caused by a CPR triggered during replay—a derived change from $A$ that overwrote a user-authored value on $B$.
   We report this as an `INDIRECT_CONFLICT` warning.

   This snapshot-based approach is more robust than inspecting the CPR engine's `PropagatedChange` output, which may not expose all consequential changes at the granularity needed for element-level conflict detection.

In the directed merge, indirect conflicts and user-vs-derived warnings are reported as non-blocking warnings, reflecting the asymmetric nature of the merge.
However, discarding derived changes from the replay can leave the model inconsistent (the reaction's effect is lost).
To address this, we additionally provide a *bidirectional merge* mode (`mergeBidirectional`): when the forward direction A→B produces indirect conflicts (derived(A) vs user(B)), the engine attempts the reverse direction B→A, where user(B)'s changes are replayed onto A and reactions fire naturally.
If the reverse direction is clean, it is used instead (reported as `REVERSED` in the result).
If both directions produce indirect conflicts, the merge is reported as a true blocking conflict (`BIDIRECTIONAL_INDIRECT_CONFLICT`), indicating that the reactions in both directions interfere with user intent on the other branch.

## Validation

We validated the implementation on two case studies.

The first case study (*Vitruvius-Branching-Test*) uses two coupled metamodels (a system/component model and a derived root/entity model) with bidirectional consistency reactions.
It covers 29 test scenarios including branch switching, pre-commit validation, changelog generation, semantic merge with conflict resolution, and bidirectional merge with direction selection.

The second case study (*BrakeCaseStudy*) models an automotive brake engineering domain with three coupled models: a brake system model ($M_1$, primary), a CAD parameter model ($M_2$, bidirectional with $M_1$), and a safety assessment model ($M_3$, derived from $M_1$).
This three-model setup exercises all conflict categories from the formalization:
clean merges where derived changes propagate across all three models without interference (3 scenarios),
indirect conflicts where a CPR triggered by replaying $A$ overwrites a user change on $B$ (2 scenarios),
a user-vs-derived warning where $A$'s explicit edit to the CAD model overwrites a reaction-derived value on $B$ (1 scenario),
a direct user-vs-user conflict on the same attribute (1 scenario),
and bidirectional merge scenarios where the reverse direction resolves an indirect conflict (1 scenario) or both directions produce indirect conflicts via the bidirectional M₁↔M₂ reactions (1 scenario).
All 36 tests (29 existing + 7 new three-model scenarios) pass, and the warning assertions confirm that the detection mechanisms correctly classify each case.
